# MXC for native Harness execution

Evaluated on 2026-11-21 against the [MXC 1.1.0 release](https://github.com/microsoft/mxc/releases/tag/v1.1.0), its tagged documentation, and the current Harness execution code. This note records the source and documentation findings. Delivery is tracked in the [native sandbox migration plan](../plans/execution/2026-11-21-mxc-native-sandbox.md).

## What to delegate

| Responsibility                    | Upstream facility                                                                                                                                                           | Harness responsibility                                                                                                                                                                                           |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Host discovery and policy support | V1 `getPlatformSupport`, `getAvailableBackends`, native policy validation, and Windows `probe`. Discovery lists available methods and capabilities.                         | Select the intended native process backend on the **server host**. Handle a refusal of the actual request even after a successful probe. Keep one default decision behind the existing server settings boundary. |
| Creating the sandbox              | Typed V1 `ContainerRequest` with `containment: { type: "process" }`. The stable SDK chooses its contract and native backend.                                                | Translate the existing resolved workspace and settings into one request. Keep direct OS calls, handwritten profiles, namespace assembly, and experimental fallbacks outside Harness.                             |
| Filesystem policy                 | `readonlyPaths`, `readwritePaths`, `deniedPaths`, and native resolution and enforcement. MXC owns the Linux mount, resolver, and seccomp setup.                             | Decide what resources to grant. Keeping file tool I/O inside the sandbox is a separate requirement from granting paths to commands.                                                                              |
| Toolchain discovery               | V1 `policy.filesystem.getAvailableToolsPolicy` discovers tool directories from a supplied environment. The profile and temporary-file helpers also return policy fragments. | Supply the trusted environment and inspect the discovered grants before applying them. Choose the private scratch path and retain workspace and Git ownership.                                                   |
| Running and stopping processes    | V1 `spawn` returns native pipes and a handle with `wait`, `kill`, and `dispose`. Use `run` only where bounded captured output fits.                                         | Adapt MXC to `SpawnedProcess`, preserving output, cancellation while starting, error classification, and completion. Keep the existing activity and output systems.                                              |
| Network and UI enforcement        | V1 directional network policy and UI controls. MXC selects the OS-specific enforcement and rejects requests it cannot represent.                                            | Choose the intended policy, explicitly map the legacy network setting, and report actual supported behavior. Start with denied UI access and no extra UI features.                                               |
| Errors and diagnostics            | Typed `MxcError`, warnings, and backend-specific denial capture.                                                                                                            | Surface actionable, redacted information through the existing server channels. Never use an allow-and-log mode as the enforcement path.                                                                          |

The [tagged Node API](https://github.com/microsoft/mxc/blob/v1.1.0/docs/api-reference/node/v1/api.md), [SDK README](https://github.com/microsoft/mxc/blob/v1.1.0/sdk/node/README.md), and [stable policy contract](https://github.com/microsoft/mxc/blob/v1.1.0/docs/containment-policy/1.0.0/policy.md) define this boundary. The SDK also has PTY and persistent-container APIs. The current native command tool uses pipes, so the replacement only needs create-and-run.

## Compatibility findings

**Linux networking is the largest behavior difference.** Harness currently uses `bwrap --share-net` for `network: true`. MXC 1.1.0 keeps the Linux process in a private namespace even with open egress. It rejects allowing ingress or host loopback and documents no IPv6 route in its slirp mode. Open egress also requires more host tooling than the existing launcher. Outbound package downloads, localhost access, and a host reaching a dev server are separate behaviors. A verified internet connection does not establish compatibility for the latter two. [Current launcher](../../packages/sandbox/src/native.ts) · [Tagged Linux network behavior](https://github.com/microsoft/mxc/blob/v1.1.0/docs/backends/bwrap/bubblewrap-backend.md#network-policy)

**Preserve broad read access with a narrow write policy.** Harness currently makes the Linux host filesystem read-only and hides host runtime and temporary directories. MXC's baseline is smaller, but explicit read-only grants can extend it. Codex uses read-only local drive roots for this purpose on Windows. The migration targets the same read/write behavior on each OS, with tests for the interactions between broad reads, workspace writes, and private runtime paths. Shell exports are already sourced by Harness and supplied separately from filesystem grants. Use SDK tool discovery for demonstrated gaps. In 1.1.0 the Windows PowerShell discovery path also proposes a history write grant, which Harness's non-interactive runs do not need. The SDK's host-temp helper returns the host temp path, whereas Harness needs private temporary storage. [Current launcher](../../packages/sandbox/src/native.ts) · [Shell environment capture](../../packages/execution/src/shell.ts) · [Linux filesystem policy](https://github.com/microsoft/mxc/blob/v1.1.0/docs/backends/bwrap/bubblewrap-backend.md#filesystem-policy) · [Codex drive-root policy](https://openai.com/index/inside-the-codex-sandbox/#drive-root-access) · [Discovery API](https://github.com/microsoft/mxc/blob/v1.1.0/docs/api-reference/node/v1/api.md)

**A common config is smaller than pretending all hosts are identical.** Windows needs native PSEC on a supported Windows 11 build, and individual capabilities such as denied paths can have additional requirements. macOS Seatbelt requires macOS 15 and has its own networking and host-tool compatibility limits. On Linux, the packaged SDK still needs usable Bubblewrap and user namespaces, with additional dependencies when enabling external egress. Use SDK discovery and one shared policy. Add platform-specific settings only where a supported workflow needs them. [Windows OS support](https://github.com/microsoft/mxc/blob/v1.1.0/docs/backends/process-container/os-version-support.md) · [macOS backend](https://github.com/microsoft/mxc/blob/v1.1.0/docs/backends/seatbelt/seatbelt-backend.md) · [Linux backend](https://github.com/microsoft/mxc/blob/v1.1.0/docs/backends/bwrap/bubblewrap-backend.md)

**Use the packaged native assets.** The Node package supports Harness's pinned Node 26.13.0, including the Windows stdio version floor. Use the existing external native dependency packaging and verify the shipped layout, license, and loading on each release target. [Tagged package manifest](https://github.com/microsoft/mxc/blob/v1.1.0/sdk/node/package.json) · [Harness packaging](../../scripts/build-payloads.mjs)

## What MXC does not replace

- **Harness authorization and scope.** The SDK enforces the policy it receives. The server still chooses the workspace, respects its existing approval policy, and owns an explicitly approved one-call host escape. Policy inputs come from trusted server state. Repository instructions and command output cannot expand grants.
- **Structured file semantics.** The Node SDK launches workloads. It provides no remote `read`, `stat`, `write`, `remove`, or glob API. Use a small one-shot Node entry point under MXC with existing file operations and glob code. Keep operation arguments and file bytes as data over pipes. Use the SDK's stream handles and verify binary I/O instead of relying on the captured text API. This limits new code to dispatch and transport.
- **Saved output and dev containers.** Trusted output persistence is existing server I/O with a separate lifetime and purpose. Docker continues to own project dev-container configuration, sidecars, and retained environments. Neither requires a new MXC abstraction.

As references, [Codex's MXC integration](https://openai.com/index/inside-the-codex-sandbox/) shows production use of Windows policy translation and targeted OS compatibility choices. It does not establish Harness parity or require copying Codex's separate Unix launchers. [Anthropic Sandbox Runtime](https://github.com/anthropics/sandbox-runtime) is useful for test and policy comparisons, but layering it alongside MXC would add a second backend and a different Windows setup model. Bubblewrap stays as an MXC Linux dependency after Harness removes its own launcher.
