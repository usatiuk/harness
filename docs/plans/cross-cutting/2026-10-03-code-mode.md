# Code mode and scoped tool discovery

Status: Complete

## Outcome

A conversation can select direct, hybrid, or code-only tools. In code-only mode
the model sees a JavaScript evaluator and ordinary search/describe tools;
discovery and nested execution use the
same permitted plugin tools, including freeform tools. Nested operations remain
recorded, governed, cancellable, and inspectable without leaking their intermediate
results into the main provider transcript.

## Design and evidence

Initial inspection found that `PluginHost.toolsFor` coupled declarations and
dispatch, the engine split call/result recording around dispatch, and activities
and subagents enriched declarations in model middleware. These boundaries needed a small
shared contract-resolution step and a recorded invocation boundary.

- Keep tool scope separate from exposure. Tool contributions default to both
  direct and code exposure; explicit flags support direct-only entry points and
  code-only/deferred capabilities. Modes select initial declarations and enforce
  model-origin dispatch independently of nested dispatch.
- Resolve effective contracts once at the turn boundary, including activity and
  subagent enrichment. Search/describe use that snapshot, with simple keyword
  ranking and bounded results through ordinary core search/describe tools.
- Core owns the evaluator entry point and scoped recorded bridge. A separate
  `code-mode` package owns a fresh QuickJS worker per invocation; protocol exposes
  only the evaluator/bridge contract. Workers keep guest computation off the
  server thread. Guest promises bridge ordinary async calls without Asyncify.
- Use host-generated child call IDs and a distinct `parentCallId` on calls and
  results. Keep the log's branch `parent` untouched. Main context excludes nested
  items; reviewer and clients see the canonical execution facts.
- Nested calls run the existing middleware chain. The evaluator wrapper is
  excluded from approval; descendants are reviewed using computed arguments and
  effective descriptions. Denials throw guest errors with result context.
- Add optional JSON structured results and output contracts, with an explicit
  content fallback for existing tools. Presentation truncation remains shared;
  bridge data, emissions, memory, computation, and submissions have fixed bounds.
- Preserve completed effects and emitted output on later failure. No script
  replay, rollback, persistent heap, durable resumption, or instruction-triggered
  yield. Stage discovered AGENTS.md after the outer result batch as today.
- Drain recorded child lifetimes before finishing the outer call. Stop admitting
  new children at completion/cancellation; explicit background activities keep
  their normal conversation ownership.
- Discovery uses immediately available `tool_search` and `tool_describe`, outside
  guest code. Both inspect the same turn-boundary snapshot; search excludes
  definitions still in context, and compaction resets that tracking.
- Evaluator identity and admission are core-owned. Reserve `eval`; do not use
  plugin metadata to bypass approval. JavaScript owns child ordering: sequential
  awaits order calls, while concurrent submissions overlap. Direct model batches
  retain their sequential loop.
- Persist structured JSON inline up to 64 KiB; spill larger JSON to the ordinary
  blob store and record a structured-output reference. Retain existing full-output
  references too. Main model context includes presentation content only. Reviewers
  get bounded structured evidence and correlated call IDs.
- Reviewer projection retains the last 16 nested calls and last 16 failures and
  their pairs, independently of compaction, derived from canonical active history. This
  prevents caught errors/denials from disappearing merely because main compaction
  intentionally omits inner execution. No duplicate approval history is stored.
- Cancellation of an evaluator awaits its worker termination and preserves
  already-emitted content, then pairs all recorded descendants before the outer
  result. Ordinary tool cancellation retains existing cooperative/abandonment
  behavior. Guest handles never escape their worker.
- Every QuickJS operation that can invoke guest code, including getters, error
  serialization, JSON conversion, and thenable settlement, consumes the same CPU
  budget. Bound names, arguments, results, and cumulative transfer bytes
  in both directions. Approval waiting consumes no guest computation budget.
- The current protocol supports text content only. `emitContent` validates that
  existing contract and rejects unsupported blocks explicitly. Adding images to
  the protocol and provider adapters is outside this first implementation; no
  screenshot/image forwarding is advertised.

QuickJS primary documentation: <https://github.com/justjake/quickjs-emscripten>.
Its explicit promises, pending-job pump, interrupt handler, memory/stack controls,
and disposable handles support this narrow worker implementation.

### Discovery correction design

The user clarified that search/describe are ordinary agent tools, not evaluator
methods, and already-loaded tool tracking resets after compaction. This supersedes
the earlier evaluator-local discovery choice.

- One scoped catalog remains authoritative. Keep existing direct/code exposure.
  The groups are immediately available tools (including discovery and eval) and
  deferred tools callable through code. No deferred model-call promotion or new
  exposure flag is required.
- Core reserves `tool_search` and `tool_describe`, presents them in every mode,
  and records their calls/results normally. They inspect catalog metadata without
  asking approval; capability execution still takes its ordinary approval path.
- Search excludes known tools before ranking/limiting and returns complete
  descriptions and input/output schemas for new matches. Repeating a query can
  therefore reach later matches. Initially declared inputs count as known for
  search. Describe is an explicit, repeatable lookup of the current full definition,
  including output schema; it allows refreshing information after configuration
  changes without a contract-version registry.
- Successful discovery results contain a core-owned annotation listing the names
  actually returned. Known names are derived from paired, successful root
  discovery results after the latest compaction on the active branch. Rewind and
  reload therefore follow canonical history; no process-local discovered registry
  is authoritative. Do not mark definitions that did not reach the main context.
- Resolve callable contracts and model declarations once per turn. Discovery
  does not alter dispatch eligibility, so guessed direct calls to deferred tools
  remain rejected. Code-only keeps ordinary operations behind `eval`, with
  search/describe as explicit immediately available control tools.
- The guest bridge becomes only `tools.call`. Core discovery tools are not
  code-callable. Query bounds and simple keyword ranking remain; returned
  definitions must fit a bounded result without silent truncation.
- Discovery is core metadata inspection, using the shared recorded invocation,
  cancellation and strict argument-parsing boundary. It does not execute through
  plugin capability middleware: approval and generic output cropping cannot
  change its own bounded definition delivery. Search packs complete definitions
  under 64 KiB and reports oversized names without marking them known; describe
  of an oversized definition returns a bounded error. Keep it sequential. No
  provider-native search integration, embeddings, replay, or new registry is
  introduced. Update the demo provider to discover normally before issuing code.
